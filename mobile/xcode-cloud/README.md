# Xcode Cloud

Builds the production iOS app (dev.suddsy.transit) in Xcode Cloud and sends
it to TestFlight / App Store Connect - an alternative to `npm run build:ios`
(EAS local build).

`mobile/ios` is generated by Expo and never committed, so this folder holds
what Xcode Cloud needs instead:

- `Transit.xcworkspace` - a committed workspace pointing at `../ios/Transit.xcodeproj`
  and `../ios/Pods/Pods.xcodeproj` (the same two projects CocoaPods' own
  workspace lists). Xcode Cloud workflows use this path.
- `ci_scripts/ci_post_clone.sh` - runs after Xcode Cloud clones the repo:
  installs Node 24 + CocoaPods, `npm ci`, `APP_VARIANT=production expo prebuild`,
  `pod install`, and sets the build number. Xcode Cloud only runs
  `ci_scripts` that sit beside the workspace, hence this folder.

Keeping it out of `ios/` means `expo prebuild --clean` can't delete it and
EAS still sees a managed (CNG) project.

## One-time setup

1. Generate the production project locally (this replaces your local dev
   `ios/` - run `npx expo prebuild -p ios --clean` afterwards to get the dev
   variant back):

   ```sh
   cd mobile
   APP_VARIANT=production npx expo prebuild -p ios --clean
   ```

2. Open `mobile/xcode-cloud/Transit.xcworkspace` in Xcode (not
   `ios/Transit.xcworkspace`).
3. Integrate menu > Create Workflow... (or the Report navigator > Cloud).
   Pick the **Transit** product, connect the GitHub repo when asked
   (grant Xcode Cloud access in GitHub).
4. Edit the workflow:
   - **Start conditions**: e.g. branch changes on `master`, files in `mobile/`
     and `packages/shared/` (so backend/web commits don't trigger a build).
   - **Environment**: latest release Xcode, latest macOS. Optional variable
     `XCC_BUILD_OFFSET` (see below).
   - **Actions**: Archive - iOS, scheme `Transit`, distribution
     **App Store Connect**.
   - **Post-actions**: TestFlight Internal Testing, pick a group.
5. Signing: Xcode Cloud manages signing automatically for team 2A422A733W.
   The app id, widget id (dev.suddsy.transit.TransitWidgets), app group,
   iCloud KVS and push capabilities are already on the App IDs from the EAS
   builds, so nothing else should be needed. If the first build fails on
   signing, open App Store Connect > Users and Access > Integrations and check
   Xcode Cloud has access.

## Build numbers

CFBundleVersion = `CI_BUILD_NUMBER` + `XCC_BUILD_OFFSET` (default 200).
EAS's remote build number was 124 when this was set up, so the first Xcode
Cloud build is 201. If you keep building with EAS too, both pipelines must
stay above each other's latest upload for the same version - simplest is to
use one or the other. Bump `version` in app.json for a new App Store version.
